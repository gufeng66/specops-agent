## 1. 一句话：这个项目是干什么的

把一段**中文会议对话 / 会议纪要**，变成一份**带原文证据的任务清单**，并且给每项任务拆出：

- **主责**（一个人，真正拍板、对结果负责）
- **次责**（可以多人，配合、协助、推进）

如果原文里确认不了谁负责（例如只写了「交给她负责」），系统**不会瞎填「待指定」**，而是停下来让人在界面上手动分配。

可以把它想成一条工厂流水线：

```text
粘贴会议原文
    → 读懂会议目标和参会人（解析）
    → 目标空了就问你一句（澄清）
    → 把句子拆成任务（拆解）
    → 检查证据、标题、负责人是否合法（校验）
    → 负责人有问题就让你选人（分配）
    → 给你看清单，批准或改（审核）
    → 导出 Markdown / JSON（导出）
```

没有 DeepSeek API Key 时，流水线照样能跑完：走的是**规则路径**（用正则和关键词猜）。有 Key 时，解析和拆解会先问大模型，失败再回退到规则。

## 2. 给小白的术语表

| 术语 | 大白话 |
| --- | --- |
| **Agent** | 不是聊天机器人那么简单，而是「按固定步骤干活的程序」。这里用 LangGraph 把步骤画成一张状态图。 |
| **LangGraph** | 把「节点 + 边」画成一张可执行的图。每个节点是一段 Python 函数；走到哪、要不要暂停，由图决定。 |
| **HITL（Human-in-the-Loop）** | 人工介入。程序算不下去时 `interrupt` 暂停，等人填完再 `resume` 继续。 |
| **SSE（Server-Sent Events）** | 服务器一边跑一边往浏览器推消息，像直播字幕，而不是等全部算完才返回一个大 JSON。 |
| **Thread / 线程** | 一次「分析这份会议纪要」的会话。有自己的 `thread_id` 和快照。 |
| **Run** | 线程里的一次执行（点「开始分析」或点「提交分配」各算一次 run）。 |
| **Snapshot / 快照** | 当前会议、任务清单、校验结果、是否在等人的完整照片，存在 SQLite 里。 |
| **Checkpoint** | LangGraph 自己的存档，记住图跑到哪一格了，这样才能暂停后再续。 |
| **幂等** | 同一个 `request_id` 点两次，第二次直接返回第一次的结果，不会把流水线跑两遍。 |
| **evidence_quote** | 任务绑定的原文引用。必须是输入文本里**连续出现过的子串**，不能改写。 |
| **unresolved_ref** | 原文用了「他/她/他们」等代词，系统不知道指谁。 |
| **规则路径** | 不调用大模型，用关键词和正则抽取。CI 和黄金评测强制走这条路。 |
| **干系人 stakeholders** | 参会人 / 负责人姓名列表。主责、次责必须落在这个名单里（有名单的情况下）。 |

三种人工介入：

| 类型 | 什么时候出现 | 你要做什么 |
| --- | --- | --- |
| `clarify` | 会议目标是空的 | 补一句目标 |
| `assign_owners` | 主责缺失、人名不在干系人里、主次冲突、代词消解不了 | 选主责 / 次责 |
| `review` | 清单已经出来，等人拍板 | 批准，或按条目/全文修订 |

HTTP 层把这三种暂停都记成状态 `awaiting_review`，前端靠 `interrupt.type` 区分弹哪块面板。

## 3. 一次完整流程（带例子）

假设你粘贴了这段话：

```text
会议目标：跟进安排
周婷：先把背景说一下。
孙磊：这个跟进交给她负责，本周内完成。
```

系统大致会这样走：

1. **intake（解析）**  
   抽出目标「跟进安排」。干系人可能从「周婷：」「孙磊：」这种发言人格式里拿到。

2. **clarify**  
   目标已经有了，这一站 **skipped（跳过）**。

3. **decompose（拆解）**  
   「这个跟进交给她负责」带动作词「负责」，会变成一条任务。但「她」对不上具体姓名，主责留空，`unresolved_ref = "她"`。

4. **validate_repair（校验）**  
   发现 `UNRESOLVED_REFERENCE` 错误。系统**不会**把主责填成「待指定」。

5. **assign_owners（分配）**  
   图在这里 `interrupt` 暂停。前端弹出绿色「分配负责人」面板，让你从干系人里选主责。

6. 你选「周婷」并提交后，图从检查点继续，再校验一次。通过则进入审核。

7. **review（审核）**  
   你点「一键批准并完成」。

8. **finalize（导出）**  
   生成按人分组的 Markdown，可以下载 MD / JSON。

前端顶部那条「解析 → 澄清 → 拆解 → 校验 → 分配 → 审核 → 导出」就是这条流水线的可视化。节点状态只有五种：`pending | running | done | skipped | waiting`。

前后端怎么连：

```text
浏览器 Vue 页面
    │  POST /api/v1/chat/stream   （开始分析 / 提交澄清）
    │  POST /api/v1/runs/{id}/resume  （分配 / 修订 / 批准）
    │  GET  /api/v1/threads/{id}/export
    ▼
FastAPI（app/main.py）
    ▼
SpecOpsWorkflow（包装 LangGraph，把节点事件转成 SSE）
    ▼
LangGraph 节点（intake → … → finalize）
    ├─ 可选 DeepSeek
    ├─ 规则抽取 / 校验工具
    ├─ SQLite 快照（MemoryStore）
    └─ LangGraph checkpoint（图游标）
```

## 5. 数据长什么样

后面几乎每个文件都在搬这几块数据，先在脑子里放一张表：

| 名字 | 装着什么 |
| --- | --- |
| `MeetingBrief` | 会议目标、干系人、日期、上下文 |
| `ActionItem` | 一条任务：标题、主责、次责、截止、验收、原文引用 |
| `TaskDraft` | 任务列表 + 版本号（每次修补 version + 1） |
| `ValidationIssue` | 一条问题：错误码、说明、ERROR 还是 ADVISORY |
| `ValidationResult` | 问题列表 + 修过几次 |
| `ThreadSnapshot` | 上面所有东西 + 线程状态 + interrupt 载荷 + 导出 Markdown |
| `AgentState` | 给 LangGraph 用的字典版快照（图节点只能读写 dict） |

线程状态 `ThreadStatus`：

- `idle`：刚创建，还没跑  
- `planning`：图正在跑  
- `awaiting_review`：卡住等人（澄清 / 分配 / 审核都用这个 HTTP 状态）  
- `completed`：已经导出

## 7. 后端：入口、配置、错误

> 本章是导读。`main.py` / `config.py` / `errors.py` 的逐步代码分析见 [Python代码详解 §1–3](./Python代码详解.md#1-backendappmainpy)。

### 7.1 `backend/README.md`

**总：** 后端自己的短说明书，指向根 README 和面试文档。

**分：** 重复拓扑、工具名单、启动和测试命令。提醒评测必须 `LLM_PROVIDER=none`。

### 7.2 `backend/pyproject.toml`

**总：** Python 项目的「身份证 + 依赖清单」。相当于前端的 `package.json`。

**分：**

- `[project]`：包名 `specops-agent`，要求 Python ≥ 3.11。核心依赖：FastAPI、Uvicorn、Pydantic、aiosqlite、httpx、LangGraph、SQLite checkpointer。
- `[project.optional-dependencies]`：`dev` 额外依赖（pytest、ruff）。运行时依赖在主依赖里。本地 `uv sync --extra dev`。
- `[tool.pytest.ini_options]`：异步测试自动开 `asyncio_mode = auto`，测试目录是 `tests`。
- `[tool.ruff]`：代码风格检查，行宽 100，忽略 E501（超长行，Prompt 很长会超）。

### 7.3 `backend/.env.example`

**总：** 环境变量模板。复制成 `.env` 后填写，程序通过 `config.py` 读取。

**分：**

| 变量 | 含义 |
| --- | --- |
| `LLM_PROVIDER` | `deepseek` 或 `none` |
| `DEEPSEEK_API_KEY` | 密钥，空则等于没用模型 |
| `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL` | 接口地址和模型名 |
| `LLM_TIMEOUT_SECONDS` | 调用超时（秒） |
| `CORS_ORIGINS` | 允许哪个前端源跨域访问 |
| `DATABASE_PATH` | 业务快照 SQLite 路径 |
| `CHECKPOINT_PATH` | LangGraph 存档 SQLite 路径 |

### 7.4 `backend/app/config.py`

**总：** 把环境变量读成一个全局 `settings` 对象。全项目只 new 一次，其他模块 `from app.config import settings`。

**分：**

- `Settings` 继承 `pydantic_settings.BaseSettings`，自动读 `.env`。
- 字段名是小写蛇形，对应环境变量是大写：`llm_provider` ← `LLM_PROVIDER`。
- 默认 `llm_provider="none"`，这样 CI 没 Key 也能跑。
- `max_tool_rounds / max_consecutive_tool_failures / max_tool_stall` 管 LLM 校验工具循环的上限，避免模型死循环修同一处。
- `cors_origin_list` 把逗号分隔的字符串切成列表，给 FastAPI CORS 中间件用。

### 7.5 `backend/app/main.py`

**总：** FastAPI 应用入口。Uvicorn 启动时加载的就是 `app.main:app`。

**分：**

1. **`lifespan`**（应用生命周期）  
   启动时：初始化 SQLite 表 → 打开 LangGraph checkpointer → 编译图 → 把 API 模块里的 `workflow` 单例换成「带真实 checkpointer 的那张图」。  
   关闭时：丢掉编译图、关闭 checkpointer。  
   为什么要「再绑定一次」？因为 `chat.py` / `review.py` 在 import 时就会 `SpecOpsWorkflow(memory_store)`，那时 checkpointer 还没 ready；lifespan 里覆盖，HTTP 请求才能用上持久化存档。

2. **CORS 中间件**  
   浏览器前端在 `localhost:5173`，API 在 `8001`，不同源，必须允许跨域。

3. **挂路由**  
   `chat_router`、`review_router`、`threads_router` 三个 APIRouter。

4. **`GET /health`**  
   返回 `{"status":"ok","llm_provider":...}`，用来确认服务活着、当前走哪家模型。

### 7.6 `backend/app/errors.py`

**总：** 业务异常。目前主要处理「同一条线程正在忙，不能并行再开一趟」。

**分：**

- `SpecOpsError`：带 `code` 的基类。
- `ThreadBusyError`：线程占用。
- `thread_busy_http()`：转成 HTTP 409，JSON 里带 `THREAD_BUSY`。前端 `sse.ts` 看到 409 会提示「线程忙碌」。

## 8. 后端：领域层 domain

这一层**不依赖 LangGraph、不依赖 HTTP**。纯数据 + 纯规则。好处：测试可以不启服务器，直接测抽取和校验。

> `models.py` / `extractors.py` / `validation.py` 每个函数的控制流见 [Python代码详解 §4–7](./Python代码详解.md#4-backendappdomain__init__py)。`extractors.py`（规则抽取）和 `nodes.py` 是后端最值得逐行读的两份。

### 8.1 `backend/app/domain/models.py`

**总：** 全项目的「数据结构合同」。用 Pydantic `BaseModel`，既能校验字段，又能 `.model_dump_json()` 存进 SQLite。

**分（按类）：**

- **`EvidenceKind`**  
  `source` = 引用原文；`inference` = 推断（必须写 `inference_reason`，且引用应为空）。

- **`MeetingBrief`**  
  `goal / stakeholders / meeting_date / context`。intake 节点的产出。

- **`ActionItem`**  
  一条任务。`id` 默认 UUID。字符串字段进模型前会 `strip()` 去首尾空格；次责列表会丢掉空字符串。  
  `unresolved_ref`：消解不了的代词。  
  `priority`：默认 `medium`。

- **`TaskDraft`**  
  `items` + `version`。每次人工分配或修补都升版本，方便看出「改过几次」。

- **`ValidationIssue` / `ValidationResult`**  
  问题码 + 严重级别。`error_issues` / `advisory_issues` / `has_blocking_errors` 是计算属性，节点里经常用。截止日期缺失是 **ADVISORY（建议）**，不会卡住流程；缺主责是 **ERROR**。

- **`ThreadStatus` / `ReviewInfo` / `ThreadSnapshot`**  
  快照是前端 `result` 事件里那一大坨 JSON 的后端形态。不包含外部工单同步状态。`graph_ns` 是 LangGraph checkpointer 的线程键，HITL 恢复时必须稳定，否则续不上档。

- **`ActionItemList` / `MeetingBriefExtract`**  
  专门包一层给 LLM 结构化输出：模型必须吐 `{"brief":{...}}` 或 `{"items":[...]}`，Pydantic 才能校验。

### 8.2 `backend/app/domain/extractors.py`

**总：** 规则路径的「眼睛和手」：从原文抽出 Brief、拆任务、改负责人、拼 Markdown。没有 API Key 时，intake / decompose 几乎全靠这个文件。

**分：**

**常量区**

- `PRIMARY_ROLE_MARKERS`：负责、统筹、主责、牵头 → 主责。
- `SECONDARY_ROLE_MARKERS`：配合、协助、推进、支持、参与 → 次责。
- `ACTION_KEYWORDS`：句子里没有这些词，规则路径就不当成任务（所以「认证模块这周也得有人看一下」这种弱表述会漏检，面试文档里写过）。
- `_has_action_keyword`：特别处理「负责人」三字——那是职位，不是「负责」这个动词。

**标题怎么剪：`_short_title`**

1. 先抠掉截止日期及其「之前/之内」邻居。  
2. 再在最早出现的角色标记（由/负责/配合…）处切断。  
3. 没有标记就在动作词处切断。  
4. 去掉「工作/任务/事项」后缀和「本次/这次」前缀。  
   例：`本次会议组织任务由周婷负责，截止时间为2026年8月7日17:30。` → 标题 `会议组织`。

**`rule_extract_brief(source_text)`**

按行扫描：

1. 用正则找「会议主题/目标/议题」当 goal。  
2. 找日期。  
3. 找「参会人：张伟、李娜」这类名单。  
4. 找「张伟：……」发言人格式。  
5. 再用百家姓 +「负责/统筹/配合」猜测正文里的人名。  
6. 干系人去重，最多 12 个。

没有「参会人：」清单时，复姓（欧阳）和英文名（Alex）进不了名单，后面主责会被打成 `INVALID_PRIMARY`。这是规则路径的已知边界。

**`needs_clarification(brief)`**  
goal 去掉空白后是空的 → 要走澄清节点。

**`extract_owners_from_sentence`**  
在句子里找已经识别出的干系人姓名：

- 同时有主责标记和次责标记：在次责标记处切开，前半主责、后半次责。典型句：「由周婷统筹，孙磊、邓凯配合」。
- 只有主责标记：第一个人名主责，其余次责。
- 只有一个人：就是主责。

**`detect_unresolved_ref`**  
句子里出现他/她/它/他们…，同时又没有任何干系人姓名 → 返回那个代词。分解时会清空主次责，交给人工。

**`rule_decompose`**

1. 丢掉「会议主题 / 参会人 / 日期」这种页眉行。  
2. 去掉「发言人：」前缀，按句号切开。  
3. 没有动作词或太短的句子跳过。  
4. 抽主次责、代词、截止日期。  
5. `evidence_quote` 必须能在原文里找到；找不到就尝试补句号、或退回整行。  
6. 验收标准先填一句模板「「标题」已完成并通过确认」（Markdown 导出时不会把这句废话展示在任务行上）。

**`patch_target_item`**  
审核阶段「单项修订」：只改目标任务的描述，其它任务 **id 不变**（前端还指着这些 id）。

**`apply_owner_assignments`**  
人工分配：只改 payload 里出现过的 `item_id`。填了主责就清掉 `unresolved_ref`。

**`render_markdown`**  
按人分节：`## 周婷（主责 n）`，主责任务带截止和配合名单；此人只是次责时写成 `配合 · 标题（主责xxx）`。没主责的进「待分配」。校验问题放「未解决问题」。文末折叠原文。

### 8.3 `backend/app/domain/validation.py`

**总：** 任务清单的质检员。规则修复也在这里，但**负责人相关错误一律不自动修**。

**分：**

**`OWNER_ERROR_CODES`**  
`MISSING_OWNER`、`INVALID_PRIMARY`、`INVALID_SECONDARY`、`PRIMARY_IN_SECONDARY`、`UNRESOLVED_REFERENCE`。这五个会把流程导向 `assign_owners`。

**`validate_task_draft`** 逐项检查：

| 错误码 | 含义 |
| --- | --- |
| `EMPTY_TASK_LIST` | 一条任务都没有 |
| `MISSING_TITLE` | 没标题 |
| `MISSING_ACCEPTANCE` | 没验收标准 |
| `MISSING_EVIDENCE_QUOTE` | source 类型却没引用 |
| `INVALID_EVIDENCE_QUOTE` | 引用不是原文子串 |
| `MISSING_INFERENCE_REASON` | 推断类型却没理由 |
| `UNRESOLVED_REFERENCE` | 代词没消解且没有主责 |
| `MISSING_OWNER` | 没主责 |
| `INVALID_PRIMARY` / `INVALID_SECONDARY` | 人不在干系人列表 |
| `PRIMARY_IN_SECONDARY` | 主责又出现在次责里 |
| `MISSING_DEADLINE` | 没截止日期（仅建议，不阻断） |

注意：有 `unresolved_ref` 且没主责时，只报 `UNRESOLVED_REFERENCE`，不再叠一条 `MISSING_OWNER`，避免面板上重复吓人。

**`repair_item` / `apply_repairs`**

- 缺验收 → 填一句通用验收。  
- 缺引用 → 拿原文第一句凑（权宜之计）。  
- 引用不在原文 → 若标题在原文里就改用标题；否则改成 inference。  
- **owner 类错误：原样返回，不填「待指定」。**  
- `EMPTY_TASK_LIST` 不在这里重新拆解（空清单是合法终态，交给人看）。

### 8.4 `backend/app/domain/__init__.py`

**总：** 包的对外出口，方便 `from app.domain import ActionItem, validate_task_draft`。

**分：** 只再导出模型和三个校验/修复函数，抽取逻辑要直接 import `extractors`。

## 9. 后端：Agent 工作流

这是项目的心脏。建议把 `graph.py` 当地图，`nodes.py` 当每一站的说明书，`workflow.py` 当「车站广播系统」（把内部事件翻译成 SSE）。

> 七个节点、四条路由、LLM 工具循环、SSE 适配的逐步分析见 [Python代码详解 §8–14](./Python代码详解.md#8-backendappagentstatepy)。

### 9.1 `backend/app/agent/state.py`

**总：** `ThreadSnapshot`（Pydantic，给 API 和数据库）和 `AgentState`（TypedDict，给 LangGraph）之间的翻译官。

**分：**

- `AgentState` 的字段几乎是快照的扁平 dict 版，另外多了运行期字段：`clarify_response`、`review_action`、`assign_action`、`pending_events`、`repair_attempts`、`assign_attempts`。
- `_replace`：LangGraph 默认会把 list **追加**合并；`pending_events` 每次节点都该是「这一站新产生的事件」，所以用 replace 语义，后来的直接覆盖前面的。
- `snapshot_to_state` / `state_to_snapshot`：进出图的时候做一次序列化 / 反序列化。模型对象进图前 `model_dump(mode="json")`，出来再 `model_validate`。

### 9.2 `backend/app/agent/graph.py`

**总：** 把节点和边焊成一张可编译的图。HTTP 运行时用的就是这张图，不是示意图。

**分：**

节点（7 个）：`intake`、`clarify`、`decompose`、`validate_repair`、`assign_owners`、`review`、`finalize`。

边（含条件分支）：

```text
START → intake
intake ──(没目标)──► clarify → decompose
intake ──(有目标)──► decompose
decompose → validate_repair
validate_repair ──(负责人 ERROR)──► assign_owners
validate_repair ──(否则)──► review
assign_owners ──(还不行且未满 3 次)──► assign_owners（自环）
assign_owners ──(否则)──► review
review ──批准──► finalize → END
review ──全文修订──► intake（整条重跑）
review ──单项修订──► validate_repair
review ──缺 item_id──► review（再审一次）
```

`WORKFLOW_NODES` / `WORKFLOW_EDGES` 给测试断言用：`test_graph_topology` 会检查图上**没有**已经删掉的 `retrieve_playbooks`（旧版假 RAG 节点）。

`build_graph(checkpointer)`：编译。没传入 checkpointer 时用内存 `MemorySaver`（测试常用）。

`bind_compiled_graph` / `get_compiled_graph` / `reset_compiled_graph`：进程级单例，和 `main.py` lifespan 配合。

`get_topology()`：从真图导出节点边，供测试，避免「文档写了但图没改」。

### 9.3 `backend/app/agent/nodes.py`

**总：** 每个车站的具体工作。文件最长，按节点读。

**公共小工具**

- `_progress(node, message, status)`：塞进 `pending_events`，workflow 再转成 SSE `progress`。
- `_tool_result`：转成 SSE `tool_result`。
- 设计点：LangGraph `astream(updates)` **只在节点结束后**才吐更新，所以不能在节点开头发 `running`。惯例是：上一站结束时帮下一站发 `running`；HITL 站不给自己发 `done`，`waiting` 由 workflow 发现 interrupt 后再覆盖。

#### `intake_node`

1. 先 `rule_extract_brief`。  
2. 若 LLM 开着，再 `structured_extract_brief`。有 goal 就用模型结果；模型没 goal 但规则也没有时，把两边非空字段 merge（`deepseek+rules`）。  
3. 若这次请求带了 `clarify_response` 且 goal 仍空，用澄清文本当 goal（澄清恢复走的是 interrupt resume，一般不走这条；这条是「第一次请求就顺便带了澄清」的兼容）。  
4. 发进度：自己 `done`；下一站 `running` 或澄清 `skipped`。

`route_after_intake`：goal 空 → `clarify`，否则 `decompose`。

#### `clarify_node`

调用 LangGraph 的 `interrupt(payload)`。payload 里 `type=clarify`。图在这里冻住，HTTP 返回 interrupt 事件。人提交后，`interrupt()` 这行「醒来」，返回用户填的文本，写入 `brief.goal`。

#### `decompose_node`

同样：规则先拆；LLM 若返回了非空 `items` 就整表替换为模型结果。然后发「得到 N 项」进度，下一站校验 `running`。

#### `validate_repair_node`

分流：

- **无 Key：`_rule_validate_repair`**  
  最多修 2 次。每次 validate → 若还有非 owner 的 ERROR 就 repair。循环后再强制 validate 一次。owner 错误故意留着。

- **有 Key：`_llm_tool_validate_repair`**  
  让模型当「调度员」，只能调三个工具：`validate_task_draft`、`repair_task_draft`、`drop_items`。  
  上限：轮次 `max_tool_rounds`（默认 4）、连续失败 2、error 数量不下降（stall）2 次就停。  
  `drop_items` **只在 LLM 模式存在**——规则路径删不掉「主题句被误抽成任务」的项。  
  循环结束后再做一次最终 validate。

`route_after_validate_repair`：有 owner ERROR → `assign_owners`，否则直接 `review`。

#### `assign_owners_node`

把当前所有 owner 错误项打包进 interrupt payload（含干系人名单、尝试次数）。醒来后 `apply_owner_assignments`，再校验。

- 仍非法且次数 &lt; 3：`assign_action.route = assign_owners`，图自环，再暂停一次。  
- 否则进 review。满 3 次仍非法时进度文案是「携带未解决问题进入审核」。

#### `review_node`

interrupt 的 `type=review`。醒来后看 `approve`：

- `true` → 去 finalize。  
- 全文修订 `revision_scope=document`：把反馈追加到 `source_text` 末尾，**整条从 intake 重跑**，分配次数清零。  
- 单项修订：必须有 `target_item_id`，`patch_target_item` 后回到 validate_repair。  
- 单项却没 id：再进一次 review，避免静默丢失。

#### `finalize_node`

调 `export_markdown_tool` 生成全文，状态改 `completed`。不写外部工单。

### 9.4 `backend/app/agent/tools.py`

**总：** 给节点调用的「确定性工具」，内部不再调用 LLM。证据硬检查走这里。

**分：**

- `validate_task_draft_tool` → `validate_task_draft`  
- `repair_task_draft_tool` → `apply_repairs`（注释写明：空列表不要重新分解）  
- `drop_items_tool`：按 id 删除任务，version + 1  
- `export_markdown_tool` → `render_markdown`

LLM 工具循环并不是让模型自己改 JSON，而是模型说「请调用某某工具」，Python 真正执行这些函数，再把结果塞回对话。

### 9.5 `backend/app/agent/events.py`

**总：** SSE 文本格式工厂。每一个函数返回一段 `event: xxx\ndata: {...}\n\n` 字符串。

**分：**

- `SSE_HEADERS`：禁止缓存、禁止 Nginx 缓冲（`X-Accel-Buffering: no`），否则「直播进度」会攒成一次性喷出。  
- 事件种类：`metadata`、`progress`、`tool_result`、`interrupt`、`token`（预留）、`result`、`error`、`done`。  
- `progress` 可带 `status`: running / done / skipped / waiting。

### 9.6 `backend/app/agent/prompts.py`

**总：** 所有给 DeepSeek 的提示词集中放这里，节点里不写长字符串。结构统一：**角色 → 技能 → 规则 → 工作流程 → 初始化**。

**分：**

- `INTAKE_SYSTEM` / `INTAKE_USER`：只抽 Brief，缺了就留空，好触发澄清；禁止编造人名。  
- `DECOMPOSE_SYSTEM` / `DECOMPOSE_USER`：证据必须是原文连续子串；不能填「待指定」；代词无法锚定就填 `unresolved_ref`；主题/寒暄不要当任务。  
- `TOOL_LOOP_SYSTEM`：调度员，不能编负责人。  
- `TOOL_SCHEMAS`：OpenAI 风格 tools 定义，喂给 `chat_tools`。

### 9.7 `backend/app/agent/workflow.py`

**总：** HTTP 运行时包装器。API 不直接 `graph.astream`，而是调 `SpecOpsWorkflow.run_chat` / `resume`。它负责：发 SSE、同步快照、识别 interrupt、幂等收尾。

**分：**

**`run_chat`**

1. 分配新 `run_id`，状态改 planning。  
2. 如果这是「澄清恢复」（带了 `clarify_response` 且已有 `graph_ns` + `interrupt_id`），用 `Command(resume=...)` 从检查点继续，**不要**换新的 `graph_ns`。  
3. 否则新开一趟：`graph_ns = thread_id:run_id`，把 snapshot 译成 initial state 送进图。  
4. 先 yield `metadata`（让前端立刻拿到 thread_id / run_id）。

**`resume`**  
审核 / 分配共用。把 approve、修订范围、assignments 打成一个 resume payload。`interrupt_type` 的对错在 API 层先拦（见 `review.py`）。

**`_stream_graph`（核心循环）**

1. 若不是 resume，先发 `intake running`（因为 intake 节点自己不会在开头发）。  
2. `async for chunk in graph.astream(..., stream_mode="updates")`：每个节点的返回 dict 里掏 `pending_events`，转成 SSE。  
3. 节点跑完后 `aget_state` 看有没有 interrupt：  
   - 有：状态写成 `AWAITING_REVIEW`，保存快照，`complete_request` 记幂等，发 `waiting` + `interrupt` + `result` + `done`。  
   - 没有：保存最终快照，发 `result` + `done`。  
4. 异常则 `emit_error` 再 `done`，避免前端一直转圈。

**`_extract_interrupts`**  
兼容 LangGraph 把 interrupt 挂在 `tasks[].interrupts` 或顶层 `interrupts` 两种形状。

## 10. 后端：HTTP API

这一层尽量「薄」：鉴权没有做（演示项目），只做参数校验、忙碌保护、幂等、把流式响应吐给浏览器。

> 请求体校验、409/幂等/澄清走 chat 不走 resume 的原因见 [Python代码详解 §15–18](./Python代码详解.md#15-backendappapischemaspy)。

### 10.1 `backend/app/api/schemas.py`

**总：** 请求体的 Pydantic 模型。FastAPI 用它自动生成校验和 422 错误。

**分：**

- `ChatStreamRequest`：`source_text`（不能空）、可选 `thread_id`、必填 `request_id`、可选 `clarify_response`。  
- `OwnerAssignment`：一条任务的主责/次责。  
- `ResumeRequest`：批准、修订范围、反馈、分配列表、`interrupt_type`。  
  校验器：如果没有 assignments，且范围是 item、又不是批准、又没 `target_item_id` → 直接 422。防止「点了提交修订却不知道改哪一条」。

### 10.2 `backend/app/api/chat.py`

**总：** `POST /api/v1/chat/stream`。开始分析，或提交澄清后继续。

**分：**

1. `claim_request`：同一个 `request_id` 已经处理过 → 立刻 SSE 回放当时快照，并标 `idempotent: true`。  
2. 澄清恢复时 `busy_thread=None`，避免「等人澄清」被误判成忙碌。  
3. 已有 thread 且正在 `planning`，或处于 `awaiting_review` 却没带澄清 → 409。  
4. 没带 `thread_id` 就 `ensure_thread(None)` 新建。  
5. 返回 `StreamingResponse`，media type `text/event-stream`。

模块顶部的 `workflow = SpecOpsWorkflow(memory_store)` 会被 `main.py` lifespan 换成带 checkpointer 的实例。

### 10.3 `backend/app/api/review.py`

**总：** `POST /api/v1/runs/{run_id}/resume`。分配负责人、修订、批准都走这里。

**分：**

1. 同样幂等。  
2. 用 `run_id` 找回快照，找不到 404。  
3. 状态必须是 `awaiting_review`，否则 400。  
4. 若请求带了 `interrupt_type`，必须和当前暂停类型一致（例如正在分配却发了 review 批准 → 400）。  
5. 把 `assignments` dump 成 dict 列表交给 `workflow.resume`。

路径里的 `run_id` 是**暂停那一次**的 run，不是 resume 新生成的那个。前端从最新 snapshot 里取。

### 10.4 `backend/app/api/threads.py`

**总：** 读线程、导出结果。不是流式。

**分：**

- `GET /{thread_id}`：整份快照。  
- `GET /{thread_id}/export?format=md|json`：json 返回快照；md 优先用已经生成的 `markdown_output`，没有就现场 `render_markdown`（审核前预览也能下）。

## 11. 后端：存储与 LLM

> SQLite 两张表、claim/complete 幂等时序、checkpointer 与 Store 为何必须两套、LLM 超时与 thinking=disabled 见 [Python代码详解 §19–22](./Python代码详解.md#19-backendappmemorystorepy)。

### 11.1 `backend/app/memory/store.py`

**总：** 业务数据库。记住「这份会议现在长什么样」，以及「这个 request_id 已经处理过」。

**分：**

两张表：

- `threads`：`thread_id` 主键，整份快照 JSON。  
- `processed_requests`：`request_id` 主键，用于幂等。

关键方法：

- `init`：建表。  
- `get_thread` / `save_thread`：读写快照，自动戳 `created_at` / `updated_at`。  
- `claim_request`：先查 request 是否存在；再如果传入了 thread_id 且该线程正在 planning / awaiting_review，抛 `ThreadBusyError`。  
- `complete_request`：`INSERT OR IGNORE`，第一次成功的结果留下来。  
- `find_by_run_id`：扫所有线程找匹配的 run（数据量演示级，可以接受）。  
- `ensure_thread`：有则返回，无则新建空快照。

全局 `memory_store = MemoryStore()`，路径来自 `settings.database_path`。

和 checkpointer 的分工：**Store 给人和 API 看；Checkpointer 给图自己看游标。** 缺一不可：只有快照没有游标，resume 不知道卡在 `interrupt()` 哪一行。

### 11.2 `backend/app/memory/checkpoint.py`

**总：** LangGraph 存档工厂。优先 `AsyncSqliteSaver`，失败则内存 `MemorySaver`。

**分：**

- `setup_checkpointer`：进程启动时打开 `CHECKPOINT_PATH`。  
- `close_checkpointer`：lifespan 结束时 `__aexit__`。  
- `get_checkpointer`：测试或过早调用时退回内存 saver。  
- `reset_checkpointer`：测试用。

### 11.3 `backend/app/llm/client.py`

**总：** DeepSeek HTTP 客户端。节点不直接写 httpx。

**分：**

- `enabled`：provider 不是 none **并且** Key 非空。缺一不可。  
- `_with_thinking_disabled`：V4 Flash 默认会「深度思考」，思维链可能拖过超时，所以请求里关掉 thinking。  
- `post_completions`：真正 POST `/chat/completions`。`asyncio.wait_for` 卡墙钟时间（httpx 的 read timeout 在流式 chunk 之间会重置，防不住「一直慢慢想」）。  
- `chat_json`：`response_format=json_object`，再 Pydantic 校验。失败抛 `LLMParseError`。  
- `structured_extract_brief` / `structured_decompose`：失败只打日志，返回 `None`，节点回退规则。  
- `chat_tools`：带 `tools` + `tool_choice=auto`，返回 assistant message（可能含 `tool_calls`）。

全局 `llm_client = LLMClient()`。评测开头会检查 `llm_client.enabled is False`，防止有 Key 时污染黄金集。

### 11.4 `backend/app/llm/errors.py`

**总：** 把「配置错 / 超时 / HTTP 失败 / JSON 对不上 schema」分成不同类型，方便日志和回退。

**分：** `LLMError` 基类带 `code`；子类 `LLMConfigError`、`LLMTimeoutError`、`LLMAPIError`（可带 HTTP 状态码）、`LLMParseError`。

## 12. 前端：页面与通信

前端几乎是**单页**：没有 Vue Router。一个 `App.vue` 管所有交互，两个子组件负责「链路条」和「按人看板」。

### 12.1 `frontend/package.json`

**总：** Node 项目清单。

**分：**

- 运行时依赖：`vue`、`marked`（Markdown 转 HTML）、`dompurify`（消毒 HTML，防止导出内容里的脚本被执行）。  
- 开发依赖：Vite、`@vitejs/plugin-vue`、TypeScript、`vue-tsc`。

### 12.2 `frontend/vite.config.ts`

**总：** 开发服务器配在 5173，并把 `/api` 代理到后端 8001。浏览器只跟 5173 说话，没有跨域问题（Docker 里通过 `VITE_API_PROXY` 指到 `http://backend:8001`）。

**分：** `timeout: 0` 是因为 SSE 可能开很久；`Accept-Encoding: identity` 避免代理把流压缩缓冲。

### 12.3 `frontend/tsconfig.json` / `tsconfig.app.json`

**总：** TypeScript 编译选项。`strict` 打开；`noEmit` 因为真正打包是 Vite。`tsconfig.app.json` 用 project references 指向前者。

### 12.4 `frontend/index.html`

**总：** 浏览器第一个打开的 HTML。只有一个空的 `<div id="app">`，由 `main.ts` 把 Vue 挂上去。标题是「会议纪要助手」。引入 Google Fonts（DM Sans / JetBrains Mono）。

### 12.5 `frontend/src/main.ts`

**总：** 三行启动：创建应用、引入全局 CSS、挂到 `#app`。

### 12.6 `frontend/src/vite-env.d.ts`

**总：** 让 TypeScript 认识 Vite 客户端类型，以及 `import xxx.vue` 是合法的。

### 12.7 `frontend/src/style.css`

**总：** 全局皮肤。深色背景、卡片、按钮、badge、输入框。CSS 变量（`--accent` 蓝、`--success` 绿、`--warn` 橙、`--error` 红）和 HITL 三种面板配色对应。小屏时 `.grid-2` 变单列。

### 12.8 `frontend/src/sse.ts`

**总：** 浏览器里没有「SSE POST」的标准 EventSource（EventSource 只支持 GET），所以自己用 `fetch` + `ReadableStream` 解析 `event:/data:` 帧。

**分：**

- `SSEHandlers`：每种事件一个回调，和后端 `events.py` 一一对应。  
- `parseSSEFrame`：一个空行分隔的帧里抽出 event 名和 data JSON。  
- `streamSSE`：  
  1. POST JSON，`Accept: text/event-stream`。  
  2. 409 → 显示忙碌。  
  3. 循环 `reader.read()`，按 `\n\n` 切帧，JSON.parse 后 switch 分发。  
  4. 流结束时把 buffer 里残留的最后一帧也处理掉。  
- `uuid()`：优先 `crypto.randomUUID`，否则自己拼 UUID v4。每次点击都会新生成 `request_id`，所以「点两次开始分析」不是幂等（那是同一 `request_id` 重放）；幂等是为了网络重试。

### 12.9 `frontend/src/Pipeline.vue`

**总：** 顶部七个点的步进条。

**分：** `NODES` 写死中文标签。父组件传入 `statuses` 字典。每种状态改圆点颜色：running 蓝发光、done 绿、skipped 变淡、waiting 橙且提示「待你操作」。

### 12.10 `frontend/src/TaskBoard.vue`

**总：** 把任务列表按人分成列：这个人当主责的卡片 + 当次责的卡片；没主责的进「待分配」。

**分：**

- `groups()`：按出现顺序收集人名，避免看板跳动。  
- 点击卡片 `emit('select', item)`，父组件用来填修订目标，并在左侧原文里选中对应句子。  
- `unresolved_ref` 用橙色标签「原文未点名 · 她」。

### 12.11 `frontend/src/App.vue`

**总：** 整个产品 UI。左栏：原文 + 时间线；右栏：HITL 面板 + 摘要 + 看板 + 校验问题 + Markdown 预览。

**分（按职责块）：**

**状态**

- `sourceText`：textarea。  
- `nodeStatus`：七个节点的状态，喂给 `Pipeline`。  
- `progressLog` / `toolLog`：时间线。  
- `snapshot`：最新结果。  
- `interrupt`：当前暂停载荷。  
- `assignDrafts`：分配面板里每条任务正在选的主次责。  
- `loading` / `errorMsg` / `threadId`。

**进度**

- `pushProgress`：写入时间线，并用 `status` 更新步进条。  
- `parseRoute`：从消息里识别「规则回退 / DeepSeek / DeepSeek + 规则」，打彩色徽章。

**跑起来**

- `runWorkflow(clarify?)`：清空日志，POST `/api/v1/chat/stream`。第一次会 `resetPipeline` 并把 intake 设为 running。  
- `resume(approve)`：POST `/runs/{run_id}/resume`。若当前是分配，带上 `assignments` 且 `approve=false`。

**原文定位**

点击任务时，用 `evidence_quote`（其次 description、title）在 textarea 里 `indexOf`，选中那一段并滚动。推断任务没有连续引用会提示原因。

分配面板有个坑：如果整行 `@click` 都会定位原文，点下拉框选人时焦点会被抢走。所以：

- 只有标题区域 `.assign-locate` 点击才定位。  
- `.assign-controls` 上 `@click.stop` / `@mousedown.stop`。  
- 选完主责后 `suppressLocate(400)` 吞掉 option 点击穿透。  
- `scripts/check-assign-select.mjs` 用正则保证这段结构以后改 UI 时不被改坏。

**三个 HITL 面板**

1. 澄清：输入目标，再调 `runWorkflow(clarifyInput)`（走 chat/stream 而不是 resume）。  
2. 分配：每条任务一个主责 `<select>` + 次责 chip 多选（主责那人不能再当次责）。  
3. 审核：默认大按钮「一键批准」；「需要修订」展开后可选单项或全文。

**导出**

`download` 直接 `window.open` 到 threads export 接口。Markdown 预览用 `marked` + `DOMPurify`。

### 12.12 `frontend/scripts/check-assign-select.mjs`

**总：** 不启浏览器的静态结构测试。读 `App.vue` 源码字符串，断言分配面板不会在 `assign-row` 上绑定 locate-on-click。

**分：** 再手写一个迷你 `isHitlInteractiveTarget`，确认点 select 时不应定位原文，点标题可以。`node` 跑这个脚本就能在 CI 之外快速防回归（当前 GitHub CI 的 frontend job 只 `npm run build`，没有跑它）。

### 12.13 `frontend/public/samples/*.txt`

**总：** 放在 `public/` 下，开发服务器以 `/samples/...` 原样提供，三个按钮 `fetch` 进来。

| 文件 | 按钮 | 设计意图 |
| --- | --- | --- |
| `demo_sprint_planning.txt` | 案例1 | 陈述句纪要，一人多任务，主次责和周期执行都写在同一句，规则路径也能抽出按人看板。 |
| `demo_incident_review.txt` | 案例2 | 事故复盘：先有非任务背景句（「先把事实对齐」），再落到可执行项。 |
| `demo_feature_review.txt` | 案例3 | 含「这个跟进交给她负责」，应进入 `assign_owners`。 |

它们**不是**黄金评测用例。黄金集在 `backend/evals/golden/`，句子更短、更模板化。

## 13. 测试、评测与样例

> 黄金集生成器/runner/打分，以及 `test_workflow.py` 里每个测试在锁什么行为，见 [Python代码详解 §23–29](./Python代码详解.md#23-backendevalsgenerate_casespy)。

### 13.1 `backend/tests/test_workflow.py`

**总：** 最大的测试文件。覆盖规则抽取、图拓扑、整条 HITL、幂等、忙碌、导出，以及用 respx mock 的 LLM 成功 / 回退 / 工具循环 / stall。

**分（按主题，不必记函数名）：**

- 图上必须有 assign_owners，不能有 retrieve_playbooks。  
- Brief / 标题剪裁 / 多人主次责 / 证据子串 / 代词。  
- 修复**不得**填写占位负责人。  
- 规则路径跑完 Demo 案例1，Markdown 按人分节且不把通用验收句铺在正文。  
- 案例3 能打出 `unresolved_ref == "她"`。  
- 工作流：澄清、分配不满 3 次会再 interrupt、批准、单项修订、文档修订重跑 intake。  
- Mock LLM：结构化成功替换规则结果；HTTP 失败回退规则；工具循环 validate 再 drop；stall 会停。

### 13.2 `backend/tests/test_api.py`

**总：** 不经过真实网络，用 FastAPI `ASGITransport` 打真实路由。

**分：** SSE 响应头是否禁用缓冲；409 忙碌；通过 API 批准；`revision_scope=document` 会改 `source_text`。

### 13.3 `backend/tests/test_llm_client.py`

**总：** 只测 HTTP 客户端两件关键行为。

**分：** 请求 JSON 里必须带 `thinking: {type: disabled}`；模拟 ReadTimeout 要变成 `LLMTimeoutError`。

### 13.4 `backend/tests/test_eval_golden.py`

**总：** 冻结评测的 pytest 入口。

**分：** 先 `write_golden()` 把模板写回 json（保证仓库里的 json 和生成器一致）→ 若 LLM 开着直接 fail → 逐个 `run_case` → `aggregate` 必须 `passed`。

门槛写死在 `evals/score.py`：任务召回 ≥ 0.9，主责 exact ≥ 0.8，次责集合相等 ≥ 0.8，HITL 是否触发与期望 **100% 一致**。

### 13.5 `backend/evals/generate_cases.py`

**总：** 黄金集的**模板生成器**。改期望请改这个文件再运行 `python -m evals.generate_cases`，不要手改大部分 json（`assign_04` 例外）。

**分：** `CASES` 列表按类型：

- `single_*`：一人一事，不需要 HITL。  
- `multi_*`：主次责拆分。  
- `assign_*`：原文没点名负责人，需要分配。  
- `clarify_*`：没写会议目标。  
- `clarify_assign_01`：既缺目标又缺负责人。

`write_golden()` 把每个 case 写成 `evals/golden/{id}.json`。

### 13.6 `backend/evals/runner.py`

**总：** 每个 case 独立的 MemorySaver + 临时 SQLite，模拟「用户会按 gold 填写澄清/分配/批准」，直到出现 `markdown_output` 或超过 12 步。

**分：**

- 开头若 `llm_client.enabled` 就抛 `EvalError`。  
- `match_item`：用 `title_keywords` 和标题+描述做重叠匹配，且一个抽出项不能匹配两次。  
- 未知 interrupt 类型直接失败（防止以后加了新 HITL 却没更新评测）。

### 13.7 `backend/evals/score.py`

**总：** 把 runner 的快照打成四个分数再平均。

**分：** `score_case` 算单条；`aggregate` 算全集并对照阈值。`hitl_ok` 看 `seen` 列表里有没有 `clarify` / `assign_owners`，与 `expect.needs_*` 比。

### 13.8 `backend/evals/golden/*.json`

**总：** 提交进 Git 的冻结输入。CI 跑评测时读这些文件（测试里也会先用生成器覆写一遍模板 case）。

**分：** 每个文件字段：

```json
{
  "id": "single_01",
  "source_text": "……会议原文……",
  "expect": {
    "needs_clarify": false,
    "needs_assignment": false,
    "items": [
      { "title_keywords": ["认证"], "primary_owner": "张伟", "secondary_owners": [] }
    ]
  },
  "gold": { "clarify": "", "assignments": [] }
}
```

- `expect`：用来打分（抽没抽到、主次责对不对、HITL 该不该出现）。  
- `gold`：runner 在 HITL 时注入的「标准答案」（澄清文本、分配给谁）。

**`assign_04.json` 是手写的代词 case**，不在 `generate_cases.py` 的 `CASES` 里。原文类似案例3：「这个跟进交给她负责」。gold 分配主责为周婷。重新跑生成器**不会**覆盖它，也不会删它。

当前黄金文件：`single_01`～`04`，`multi_01`～`04`，`assign_01`～`04`，`clarify_01`～`02`，`clarify_assign_01`。

## 15. 设计边界与常见误解

请和小白（以及面试官）提前对齐：

1. **没有知识库 / 向量 RAG。** 旧节点 `retrieve_playbooks` 已删除。  
2. **不会真的写入 Jira / 飞书。** 代码里没有同步字段，也没有适配器。  
3. **没有登录、租户、限流、密钥托管。** `.env` 仅本地。  
4. **黄金集 0.9 是规则路径回归，不是「模型有多聪明」。**  
5. **规则路径会漏：** 复姓/英文名、主题句带「推进」、弱动作词、同一发言里第二句没有关键词。案例1 故意把「人名和动作写在同一句」，就是为了让无 Key 也能演示看板。  
6. **「交给她」进人工分配是功能，不是 bug。**
