# 会议任务解析 Agent 面试题库（短版）

面向初中级到中级 Python 后端 / LLM 应用岗位。短版只收主线问题，每题答案按面试现场可直接口述来写；追问时再展开完整合并版中的设计细节。

> 口径说明：以下描述以当前仓库实现为准。真实 API 评测仅覆盖七个手写 hard case，不代表真实业务准确率；幂等并发、语义裁判、人工覆盖负责人错误等限制会主动说明。

---

## Q1. 介绍一下这个项目，它解决什么问题？

我做的是一个会议任务解析 Agent，把中文会议对话或纪要整理成可审核、可导出的任务清单。每条任务会尽量保留原文证据，并拆出主责和次责；目标不清楚时会先让人补充，负责人无法确认时会进入人工分配，最后由人审核后导出。这个项目关注的不是把会议总结得更像一篇文章，而是让任务从哪句话来、负责人是否确定、还有哪些事项没闭环都能被检查。现在它是一个可运行的 MVP，支持 Markdown 和 JSON 导出，没有接企业工单系统，也没有登录和多租户能力。

## Q2. 说说整体架构和一次请求的处理过程。

前端是 Vue 3，后端是 FastAPI，流程用 LangGraph 编排。用户提交会议文本后，后端运行 intake、目标澄清、任务拆解、校验修复、负责人建议和人工审核这些节点；节点进度通过 SSE 发给前端。遇到需要人决定的节点，图通过 interrupt 暂停，前端提交答案后，后端用同一条图的 checkpoint 恢复。SQLite 里另外保存给界面使用的业务快照，两类存储用途不同：checkpoint 记图执行到哪，快照保存任务和审核状态。没有 LLM Key 时可以走规则路径；有 Key 时模型参与拆解或给负责人建议，但不会因此绕过人工审核。

## Q3. 为什么选固定流程图，而不是开放式自主 Agent？

这个任务的主要风险是抽错任务或把责任放错人，所以我把流程和工具范围做成有限、可检查的图，而不是让模型自行规划下一步、调用任意工具。需要人判断的地方有明确暂停点，模型输出也要经过校验；修复和分配循环有上限，避免流程无限重试。它不是开放式自主 Agent，更接近一个带 LLM 能力、带人工介入和恢复机制的工作流。这样做牺牲了一些灵活性，但能清楚地说明每个环节谁在做决定、哪里可以恢复、哪些结果还需要人确认。

## Q4. 原文证据解决了什么问题？它能证明任务正确吗？

证据字段的作用是让审核者能回到会议原文检查模型引用的内容。当前硬校验能验证原文型引文是否确实出现在输入里，避免模型把改写或拼接的句子伪装成原话；但“引文存在”不等于“引文支持这条任务”，语义相关性没有被规则硬校验。抽取提示会要求任务和证据相对应，终审时人也可以删掉不相关任务，但我不会说系统已经解决了证据相关性。对 ASR 错字也采用严格校验会误伤部分正确证据，这是明确的取舍，仍需要人工处理。

## Q5. 负责人如何分配？人工确认是不是只是走形式？

模型给负责人候选建议时只写入单独的建议字段，不直接改主责或次责字段；真正写入需要人工在分配面板提交，或在审核阶段批准。负责人缺失、代词无法消解等情况会触发人工分配，系统不会把“待指定”当成真实负责人。不过这里有个实际边界：分配尝试达到上限后，流程会带着仍未解决的 ERROR 进入终审，终审允许人显式批准。因此人工确认能阻止模型未经操作直接落责，但不能保证人一定识别并拒绝错误结果；我会把它说成风险控制，不说成绝对安全保证。

## Q6. 中断后怎么恢复？幂等和并发保护做到什么程度？

图的 checkpoint 记录执行位置，SQLite 快照保存界面需要展示的任务状态；人工提交后，LangGraph 会从对应的中断位置继续。同一线程已经在运行时，新的运行请求会被忙碌保护拒绝；已完成并记录的 request_id 可以回放第一次的结果。当前幂等实现还有缺口：记录没有 TTL，同一个 ID 会一直命中旧结果；请求开始时也没有原子占位，所以并发到达的相同 ID 可能同时通过检查。更完整的方案应该把幂等键限定到用户和操作范围，设置过期时间，并在处理开始时原子写入处理中状态。这是我会优先补的可靠性问题，不是当前已经解决的能力。

## Q7. 模型不可用或输出不合格时，系统怎么处理？

项目保留了规则路径，没配置 Key 时可以完成基本流程和演示；模型输出还会经过结构和字段校验，负责人错误不会交给自动修复去猜。模型调用对部分 429、5xx 和传输错误做有限重试，超时不重试，避免一次请求无限等待。校验修复循环和负责人分配都有上限，失败或无法继续时会停在可审核的状态，而不是无限调用模型。需要区分的是，规则回退让流程在无模型时仍可运行，但不代表规则抽取质量和模型相同；规则在弱动作词、复姓等场景仍有漏检或误检。

## Q8. 你怎么评估模型效果？能给出实际结果吗？

我分别跑过 rules、hybrid 和 llm_only 三种模式，使用七个手写 hard case 做一次真实 API 对照。报告中 rules 的任务召回率是 0.714、精确率是 0.857；hybrid 的召回率升到 1.000，但精确率降到 0.548；llm_only 在这组样例上是 1.000 和 1.000。三种模式在这组样例上的负责人幻觉率都是 0。这个结果能说明混合方案补回了规则漏检，同时也带来假阳性，不能说明真实业务准确率是 100%。仓库里的冻结回归集主要检查流程契约和规则行为；这次真实 API 报告没有触发语义 judge，所以我没有可报告的模型语义召回分数。

## Q9. 这个项目里你遇到的关键取舍或问题是什么？

我遇到的一个具体取舍是规则漏检和模型假阳性之间的平衡。规则路径比较可控，但在弱动作词、复姓等手写难例上会漏任务；加入模型后，这次七例实验的召回从 0.714 提到 1.000，但 hybrid 精确率从 0.857 降到了 0.548。这个结果让我不能简单说“加模型就更准”，而要分别看漏检和误报，并保留人工审核。下一步我会扩大并人工标注真实会议样本、重复运行不同类型输入，再评估模型带来的质量变化；当前数据集规模不足以支撑泛化结论。

## Q10. 如果准备上线，你会先补什么？

当前项目缺少登录鉴权、多租户隔离和入口限流，密钥管理也只是本地环境变量，因此不能直接作为多租户生产服务。幂等记录需要增加原子认领、范围限定和过期策略；还要补待处理人工任务的可见队列和超时提醒。目前没有对外创建工单或发通知的集成。上线时我会先补鉴权、租户隔离和密钥托管，再完善幂等与监控告警；外部写入则放在人工批准之后，并设计好幂等和失败补偿。模型效果评测也需要扩充为有人工标注的真实会议集，再决定是否满足业务要求。

## 口述时的边界

- 原文子串校验验证的是引文存在，不是任务与引文的语义相关性。
- 人工审核限制模型直接写入，但人仍可批准带负责人 ERROR 的清单。
- 七个 hard case 的真实 API 结果是一次有限实验，不是通用准确率。
- 本次报告未触发语义 judge，没有语义召回结果可引用。
- request_id 当前没有过期时间，也没有并发原子认领。
- 待办催办、登录、多租户、入口限流和外部工单写入都未实现。
