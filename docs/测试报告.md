### 本次新增：图路由单测

`tests/test_graph_routes.py` 把 `app/agent/graph.py` 四个条件边的决策逻辑固化成断言，此前这类状态机分支只被端到端流程间接覆盖。

- `route_after_validate_repair`（7）：owner ERROR → `propose_owners`；无错误 / 非 owner 错误 / 仅 advisory / 字段缺失 → `review`
- `route_after_propose`（4）：仍有 owner ERROR → `assign_owners`，否则 `review`
- `route_after_assign`（6）：节点再次要求分配则重入；action 缺失、空路由、未知路由均回落 `review`；`MAX_ASSIGN == 3`
- `route_after_review`（7）：四个合法路由透传；approve → `finalize`；**全文修订 → `intake`**；**单项修订 → `validate_repair`**；删除后再审 → `review`
- HITL 状态标记（19）：owner 错误码全部识别、非 owner 错误不识别、降级为 advisory 后不算 ERROR

注意「全文修订」的去向：`app/agent/nodes.py:828-843` 中 `revision_scope == "document"` 写的是 `route: intake`（并把 `[文档修订]` 追加进原文），进入 `validate_repair` 的是单项修订（`nodes.py:855-868`）。这与 `route_after_review` 的 docstring 一致。

## 四、本地端到端

`frontend/e2e/sample-flow.spec.ts` 会拉起无 Key 后端（127.0.0.1:8001）与 Vite（127.0.0.1:5173），走示例3 的分析、分配、审核和导出。

**修复的一条既有失败**：检查点等待元素用的是 `getByText('审核任务清单')`，默认 `exact: false` 做子串匹配，同时命中了 4 处——时间线的 `running` 与 `waiting` 两条进度、审核面板的 `<h3>` 标题、以及面板里渲染中断消息的 `<p>`，触发 Playwright 严格模式冲突。

排查结论是**测试选择器过窄，不是产品缺陷**：

- 时间线里 `review / running → waiting` 两条是后端既有设计（`nodes.py` 的 review 节点发 `running`，`workflow.py:222` 检测到中断再发 `waiting`），`assign_owners` 同样是 `running → waiting → done` 三段式；
- 前端 `pushProgress`（`App.vue:115-125`）是纯 `push`，无合并与重发，每个节点恰好一条，不存在重复渲染或事件丢失。

改为按语义定位真实面板：

```ts
await expect(page.getByRole('heading', { name: '审核任务清单' })).toBeVisible({ timeout: 60_000 })
await expect(page.locator('.hitl-review')).toBeVisible()
```

不加 `timeout` 之外的重试：`--repeat-each=3` 三并发复跑同样 3 passed，无 flaky。
